1  The big picture

Baymax is a Chrome extension (Manifest V3). A Chrome extension is split across isolated JavaScript worlds that cannot call each other's functions directly — they can only pass messages. The whole guide engine is an exercise in shuttling one small message across those worlds and back:

ui Side panel
A React app (the extension's UI)
  • Guidance/index.jsx — the director
  • guide.js — the messenger
  • guides/*.js — the scripts (imported data)
Chrome APIs
The message bus between worlds
  • chrome.tabs.sendMessage → page
  • chrome.runtime.sendMessage → panel
  • chrome.tabs.onUpdated (navigation)
  • chrome.webNavigation.getAllFrames
page Content script
Injected into console.cloud.google.com
  • guide-overlay.js — the hands
  • Runs inside every same-origin frame
  • Owns the mascot + highlight (Shadow DOM)
index.jsx → calls → guide.js → chrome.tabs.sendMessage → guide-overlay.js  (command: highlight / click / fill)
guide-overlay.js → chrome.runtime.sendMessage → listener in guide.js → callback → index.jsx  (event: CLICKED / FILLED / DISMISSED / GO_BACK)
static data side-panel logic messaging bridge runs on the GCP page
The one sentence to remember: index.jsx reads a step from a guide file, hands it to guide.js, which serialises it into a BAYMAX_GUIDE message that guide-overlay.js turns into a real highlight on the page. When the user acts, the reverse trip fires a BAYMAX_GUIDE_* event that tells index.jsx to advance — and each completed step is persisted to the backend as it happens.

2  Why messages instead of function calls

The side panel and the page are different origins in different processes. The panel is a chrome-extension://… document; the page is https://console.cloud.google.com. They share no variables, no DOM, no globals. Two channels bridge them:

Direction API Carries Lives in
Panel → Page chrome.tabs.sendMessage(tabId, msg, {frameId}) A BAYMAX_GUIDE command (highlight, click, fill, clear, snapshot, record-start/stop) guide.js › sendGuideCommand()
Page → Panel chrome.runtime.sendMessage(msg) A BAYMAX_GUIDE_* event (user clicked / filled / dismissed / go-back) or a BAYMAX_RECORD_ACTION guide-overlay.js › send() → listeners registered by guide.js
Browser → Panel chrome.tabs.onUpdated URL changes of the pinned guided tab only (incl. SPA route changes) guide.js › onGcpUrlChanged()
New: the pinned guided tab. All tab-touching operations resolve through getGuidedTab(). The first command of a run adopts the active Console tab and remembers its id in guidedTabId; from then on the guide follows that tab — focused or not — so another GCP tab can't hijack highlights, flag off-track, or auto-advance a step. A pinned tab that navigates away from the Console is treated as unavailable, but the pin is kept so the guide recovers the moment the user brings it back; a closed tab drops the pin. resetGuidedTab() is called on a fresh Guidance mount and at startRecording() so a new run adopts the tab the user is on now.
The iframe wrinkle. The GCP Console renders most pages inside a same-origin <iframe>. A content script is injected into every frame, and sendMessage only reaches frame 0 by default. So guide.js asks chrome.webNavigation.getAllFrames for the full frame list and broadcasts the command to all of them, keeping the first frame that answers {ok:true}.

4  data The scripts — src/lib/guides/

baymax-extension/src/lib/guides/cloudSqlPostgres.js  ·  cloudRun.js

These files have no logic — each exports one guide object with an id, a title, optional prerequisites/nextSteps, and a steps[] array. Every other file's behaviour is driven by the fields on these step objects: a small domain-specific language whose "interpreter" is spread across the other three files.

  • cloudSqlPostgres.js — the 10-step Cloud SQL guide; still the built-in default when there is no explicit guide and no session.
  • cloudRun.js — an offline copy of the official "Host a backend on Cloud Run" guide. The live version is served from the backend (recorded_guides rows with is_official; extras like prerequisites/nextSteps/task id travel under meta). App.jsx fetches it on chip tap and offers this bundled copy only if the fetch fails and the user accepts the offline prompt. Keep it in sync with baymax-backend/data/official_cloud_run_guide.json.

The step vocabulary — what each field controls, and who reads it

Field What it does Read by
id Stable step identifier index.jsx (backend status updates)
title / description Text shown in the step card, the speech bubble, and read aloud index.jsx, overlay (bubble)
action 'click' | 'fill' | 'highlight' — what "Do it for me" performs and whether a click completes the step index.jsx, guide.js, overlay
selector Comma-separated CSS fallbacks. Also the progress key the click/fill watchers report under overlay (resolver), index.jsx (compare)
value Text to type for a fill step overlay (fill)
name / text / role / href Semantic intent — the resilient resolver prefers these over the brittle selector overlay (scoreCandidate)
exactName Require a whole-string name match (rejects "Cloud SQL for MySQL" when we want "Cloud SQL") overlay
avoidText / avoidHref Disqualify / penalise look-alikes ("Enterprise Plus", the Marketplace link) overlay
requireSelector Only match the step's own selector — skip the generic element scan (for common words like "Cloud SQL") overlay
revealSelector / revealValue new The control that re-summons a transient panel the target lives in (e.g. the search-suggestions dropdown, which closes when the side panel takes focus): focus/click it, refill revealValue if empty, wait 900ms, re-resolve overlay (tryReveal)

Regex tolerance. Recorded and AI-generated guides can carry a urlPattern that isn't a valid regex. guide.js › safeMatch() catches the RegExp throw and the caller picks the safe default: an invalid urlPattern counts as "always on track", an invalid advanceOnUrlPattern as "never auto-complete".

Reading the 10 Cloud SQL steps as a state machine

The guide is a linear machine, but two mechanisms let it skip around: advanceOnUrlPattern (jump forward when the page proves a step is done) and urlPattern (flag "you wandered off").

  • Steps 1–2 — the search lead-in (page-agnostic). No urlPattern, so they work from any console page. Step 1 fills "Cloud SQL" into the top search box; step 2 clicks the product result. Both share an advanceOnUrlPattern that matches any Cloud SQL page except the create/picker pages — the instant the tab lands there they auto-complete. Step 2 uses exactName+requireSelector because "Cloud SQL" also appears as left-nav branding.
  • Step 3 — "Create instance". Lives on the Cloud SQL landing page (urlPattern excludes the create form). The href:'/sql/choose-instance-engine' tips the resolver toward the direct link on the empty-state page, so the no-instances flow jumps straight to the engine picker.
  • Step 4 — "New instance" menu item. Only exists when the project already has instances (a dropdown). When the list is empty there's no menu, so autoSkip + advanceOnUrlPattern quietly skip this step.
  • Step 5 — "Choose PostgreSQL". The engine picker. Its urlPattern is only the picker, and advanceOnUrlPattern:'engine=PostgreSQL' — so choosing MySQL doesn't advance and instead goes off-track (Take me back).
  • Steps 6–9 — fill/pick the form. All pinned to urlPattern:'engine=PostgreSQL': instance ID (fill), password (highlight only — never auto-typed), region (combobox), Enterprise edition (avoidText:'plus' so it skips "Enterprise Plus").
  • Step 10 — "Create instance" submit. awaitNavigation:true: the click alone isn't success. Only navigating to /sql/instances (its advanceOnUrlPattern) proves the instance was created; otherwise the guide stays put and asks the user to fix the flagged fields.

5  ui The director — Guidance/index.jsx

baymax-extension/src/pages/Guidance/index.jsx

This React component is the brain. It holds "which step are we on", subscribes to page events and URL changes, and for every situation decides one of four outcomes: highlight the step, auto-advance past it, show off-track ("Take me back"), or show a status message.

5.1  State & the derived "current step"

const [stepIndex, setStepIndex] = useState(0)   // ALWAYS starts at 0 — no localStorage
const [steps, setSteps]         = useState([])  // the actual step array in use

const safeStepIndex = steps.length ? Math.min(stepIndex, steps.length - 1) : 0
const step         = steps[safeStepIndex]   // ← THE object everything below acts on
const isLastStep   = safeStepIndex === steps.length - 1
Changed: progress has ONE source of truth — the backend. The old localStorage store (keyed by guide id) was a second, competing source: every task and re-run of the same guide shared one key, so a fresh start inherited the last run's abandoned step. Now markStepStatus(index, status) is the single write path — fire-and-forget PATCH /sessions/{id}/steps/{step_id}, a no-op without a session (recorded guides / offline). Resume happens only through the backend: listSteps → land on the first step whose status isn't completed/skipped. The arrival effect (keyed on step.id, not the index) marks each newly-current step in_progress.

safeStepIndex is a defensive clamp: a resumed index can point past the end of a (possibly shorter) step list, which would make step undefined and crash the panel on step.title. Clamping keeps the render safe while an effect snaps the stored index back into range.

The refs that make navigation sane

Ref Purpose
advancedRef One-shot latch so a step can't auto-advance twice (e.g. click and URL change both fire).
backPressedRef Set when the user presses Back, so a stale later-page URL doesn't immediately bounce them forward again. Cleared on any forward move. Now also gates the auto-advance checks themselves (both in checkStep and the URL listener).
hiddenRef Set when the user dismisses the mascot with × — suppresses re-highlighting until "Show me".
maxReachedRef The frontier: the furthest step ever reached. URL auto-skip is only allowed at/above the frontier (see below).
stepIndexRef new Live mirror of stepIndex so delayed callbacks ("Do it for me"'s 800ms advance timer) can tell whether the guide already moved on since they were armed.
submitTimerRef The pending "did the submit actually work?" check for an awaitNavigation step; cleared on every step change.
The frontier rule — the trickiest idea in the file. advanceOnUrlPattern exists to skip steps the page has genuinely moved past. But if the user presses Back to redo step 3 while the tab is still parked on the create-instance form, that stale URL satisfies the advanceOnUrlPattern of steps 3, 4, 5… and would cascade them straight back to step 10. So URL-based advancing only fires when atFrontier() (stepIndex >= maxReachedRef) — or for explicit autoSkip steps once the tab has physically left the step's own page — and never while backPressedRef is set. Below the frontier, only a real click/fill or the Next button advances, one step at a time.

5.2  Loading the steps (local sources are authoritative)

The load effect fills steps from whichever source applies — in this order:

  1. An explicit guide prop (a recorded guide, the official Cloud Run guide, or the built-in mock passed from App) → use guide.steps. Used even when a sessionId exists.
  2. dynamicGuide (an AI blueprint from chat) → use its steps. Also wins over a session.
  3. No sessionId → fall back to the built-in CLOUD_SQL_POSTGRES_GUIDE.steps.
  4. A backend session and no local copy (i.e. resuming) → api.listSteps(sessionId), then land on the first step that isn't completed/skipped.
Why local wins: the backend session copy is lossy — schemas/step.py drops the resolver fields (name, exactName, avoidText, awaitNavigation, …). It must never replace live local steps, even when the sessionId arrives mid-run; it's only used when resuming, where the saved copy is the only source there is.

5.3  The heart: the "on step change" effect

Every time the current step object changes, the effect runs checkStep() — the decision tree that decides what the user sees. Read it top-to-bottom — order matters:

1
Bail if hidden. If the user dismissed the mascot (hiddenRef), do nothing.
2
Ask the guided tab where it is. await getCurrentGcpUrl() (the pinned tab, via guide.js).
3
Already done? If !backPressedRef and stepCompletedByUrl(step, url) and (frontier, or an autoSkip step that has left its page) → autoAdvance() and stop. This is what makes steps 1–2 vanish when you're already on Cloud SQL.
4
On the wrong page? If the step has a urlPattern and the tab isn't on it → set offTrack, show the status message, and showLostMascot(). Crucially, it does NOT scan the wrong page for a same-named look-alike.
5
Try to highlight. Otherwise call highlightStep(step, mascotExtras). If it returns {ok:true} → clear off-track/status and we're done.
6
Not found on a page-agnostic step, and not on its page either? → off-track + lost mascot, rather than highlighting whatever shares the name.
7
Not found → retry. On 'not-found', retry up to HIGHLIGHT_RETRIES (6) times, 700ms apart — the element may not have rendered yet (SPA still loading, dropdown opening).
8
Give up gracefully. After retries, show the mapped status message ("Navigate there manually…"). The self-heal LLM round-trip that used to run here is commented out — SELF-HEAL DISABLED.

The cleanup sets cancelled = true so an in-flight retry/await from the previous step can't fire after we've moved on — a classic React async-effect guard.

Changed: these effects are keyed on the step OBJECT, not the index. steps arrives asynchronously (mock, prop, or backend fetch); an index-only dependency left the effects dormant on a fresh start — mounted at step 0 with an empty array, they never re-ran when the steps filled in. Voice is also its own effect now, keyed on the spoken text (`Step N: title. description`), so an id-merge that replaces the steps array with an equivalent copy neither cuts off nor restarts the announcement.

5.4  The two subscription effects

URL changes → advance or flag off-track

onGcpUrlChanged fires for every navigation of the pinned tab:

  • If !backPressedRef and stepCompletedByUrl and (frontier or autoSkip-left-page) → autoAdvance(). This is how clicking a search suggestion — something we never explicitly watched — still completes the step.
  • Else if the step has a urlPattern and we're not on it → immediately show off-track (no 1.2s wait, no scanning the wrong page — which could flash a stray "PostgreSQL" highlight on the MySQL form).
  • Else, after a 1200ms debounce (let the SPA settle), try highlightStep again; if that says 'not-found' and the tab isn't on the step's page, show off-track.

Page events → advance

onGuideStepEvent({
  onClicked: (selector) => {
    const stepKey = step.selector || step.name          // same fallback the overlay reports under
    if (step.action !== 'click' || selector !== stepKey) return  // only a real click-step completes on click
    if (step.awaitNavigation) verifySubmit()          // submit steps: wait for navigation
    else autoAdvance()
  },
  onFilled: (selector) => {                          // typed a value OR picked a dropdown option
    if (selector === (step.selector || step.name)) autoAdvance()   // NOT gated on step.action
  },
  onDismissed: () => { hiddenRef.current = true; setStatusMessage(HIDDEN_MESSAGE) },
  onGoBack:    () => handleTakeMeBack(),
})
Why the click gate matters. On a highlight step (like the Region dropdown), clicking the control merely opens it — the user still has to pick a value — so onClicked deliberately ignores it (step.action !== 'click'). The actual selection arrives later as an onFilled event (the overlay's watchOptionSelect reports the chosen option as a fill).

5.5  The buttons (explicit user commands)

Handler What it does
handleShowMe Un-hide, then either offer Take-me-back (wrong page) or highlightStep again.
handleDoItForMe runStepAction(step) → overlay clicks/fills for the user. For a submit step, verifySubmit(); else auto-advance after 800ms — but only if the guide is still on the step the button was pressed on (stepIndexRef guard: a navigating click may have advanced it already, and arriving at the new step resets advancedRef, so that latch alone can't stop a double-advance).
handleTakeMeBack goToStepPage(step) (verified browser Back, or the step's url), then re-highlight after 1.5s.
goNext / goPrev Manual navigation. goNext marks the departing step completed on the backend; on the last step it calls finish() (marks the session completed + celebration screen). goPrev sets backPressedRef.

verifySubmit() — the anti-false-positive guard

const verifySubmit = () => {
  clearTimeout(submitTimerRef.current)
  setStatusMessage('')
  submitTimerRef.current = setTimeout(async () => {
    if (advancedRef.current) return                 // navigation already advanced us → success
    const tabInfo = await getCurrentGcpUrl()
    if (tabInfo?.ok && stepCompletedByUrl(step, tabInfo.url)) return
    setStatusMessage(SUBMIT_BLOCKED_MESSAGE)          // still on the form → GCP rejected it
  }, SUBMIT_VERIFY_MS /* 2200ms */)
}

A successful "Create instance" navigates to the instances list within ~2.2s, and onGcpUrlChanged will already have advanced the guide. If we're still on the form after the timeout, the create was rejected — so instead of celebrating, Baymax tells the user to fix the flagged fields.

6  bridge The messenger — guide.js

baymax-extension/src/lib/guide.js

Every function here is a thin adapter between "a step object" and "a Chrome message". It never touches the DOM of the GCP page — it only talks to the content script. There are three groups: commands (panel → page), subscriptions (page → panel), and pure helpers (URL logic + recording generalisation).

6.1  The pinned tab & frames

let guidedTabId = null   // the ONE Console tab this run follows

async function getGuidedTab() {
  if (guidedTabId != null) {
    try {
      const tab = await chrome.tabs.get(guidedTabId)
      return GCP_ORIGIN.test(tab.url || '') ? tab : null  // left the console → unavailable, pin kept
    } catch { guidedTabId = null }                          // tab closed → re-adopt below
  }
  const [tab] = await chrome.tabs.query({ active: true, currentWindow: true })
  if (!tab || !GCP_ORIGIN.test(tab.url || '')) return null
  guidedTabId = tab.id                                       // ← adopt (pin) the active tab
  return tab
}

isExtensionContext() guards every entry point so the same code runs harmlessly in a plain browser tab (during dev) where chrome.tabs doesn't exist — functions return a tidy {ok:false} instead of throwing.

sendGuideCommand(message) — the broadcast core

1
Get the guided tab (pinned, or adopt the active GCP tab), or return {ok:false, error:'no-gcp-tab'}.
2
Ask chrome.webNavigation.getAllFrames for every frame (falls back to just frame 0 if unavailable).
3
Send the message to each frame in turn; return the first {ok:true}. Frames with no listener (about:blank) just throw and are skipped.
4
If none succeeded, return the last error (e.g. 'not-found') so the panel can react.
Dead code alert (see §0). The function also contains a block that would clear stale overlays in the other frames after a success, plus a sibling broadcastGuideCommand() ("ok if ANY frame acknowledged" — intended for clear and recording). The block is unreachable due to a shadowed result variable and the helper is never called — so today every command, including clear, is first-answer-wins.

Every command wrapper — highlightStep, runStepAction, showLostMascot, clearGuideHighlight, startRecording, stopRecording — is a one-line call to sendGuideCommand with a different action. Note the renames as data crosses the boundary: the step's description becomes the message's message, and the step's action becomes stepAction (so it doesn't clash with the message's own action:'highlight'). runStepAction maps step.action to the message's action (fill vs click) and includes value. Both also forward extraSelector (self-heal channel) and revealSelector/revealValue.

6.2  The subscription side (page → panel)

export function onGuideStepEvent({ onClicked, onFilled, onDismissed, onGoBack }) {
  const listener = (msg) => {
    if (msg?.type === 'BAYMAX_GUIDE_CLICKED')   onClicked?.(msg.selector)
    if (msg?.type === 'BAYMAX_GUIDE_FILLED')    onFilled?.(msg.selector, msg.value)
    if (msg?.type === 'BAYMAX_GUIDE_DISMISSED') onDismissed?.()
    if (msg?.type === 'BAYMAX_GUIDE_GO_BACK')   onGoBack?.()
  }
  chrome.runtime.onMessage.addListener(listener)
  return () => chrome.runtime.onMessage.removeListener(listener)   // unsubscribe
}

onGcpUrlChanged(cb) wraps chrome.tabs.onUpdated — but now filters by identity, not focus: only the pinned guidedTabId drives the guide. Another GCP tab can't flag off-track or auto-advance just because the user switched to it while it navigated — and a guided-tab navigation that finishes while the user is elsewhere still counts. No pin yet ⇒ the event is ignored (adopting from a navigation would pin whichever tab happened to move first).

6.3  The pure URL helpers

Function Logic
isOnStepPage(step, url) No urlPattern (or an invalid one) → always true ("location-agnostic"). Else test the regex via safeMatch.
stepCompletedByUrl(step, url) No advanceOnUrlPattern (or an invalid one) → never auto-complete. Else test the regex.
goToStepPage(step) chrome.tabs.goBack first (preserves the user's place), then verifies: wait 500ms for the SPA route to settle, re-read the tab, and if it still isn't on the step's page (a multi-page wander) fall back to hard-navigating to step.url — also the fallback when there's no history at all.

6.4  captureSnapshot() — the self-heal collector (currently disabled in index.jsx)

Unlike the commands, this one does not take the first frame that answers. The element being hunted could be in any iframe, so it queries every frame, merges all their element lists (deduped by selector|name|href), and caps the result at 120 elements so a busy page can't blow up the LLM prompt. It's the "read the whole page" half of the self-heal feature.

6.5  Recording & generalisation

The recorder lets a user capture their own guide. startRecording() first calls resetGuidedTab() — a recording targets the tab the user is on right now, not one pinned by an earlier run — then toggles capture on the page; onRecordedAction(cb) streams each captured action back. The interesting logic is generalising a recorded step so it replays on any project/instance:

  • volatileTokensFromUrl(url) — pulls the volatile identifiers out of the URL: the project=… query values and the instance/resource path segment (with a stop-word list so console path words like instances, overview are never mistaken for ids).
  • detectInstanceSpecific(name, text, url) — true when a recorded label embeds one of those tokens (e.g. "View more actions for my-instance-a"), so the "Match any instance" toggle is worth offering.
  • applyGeneric(step) — strips those tokens from name/text, drops a selector pinned to them, and loosens exactName to a contains-match — so the step matches the same control on a different instance.
  • recordedActionToStep(action, index) — converts a raw fingerprint into a guide step, turning fill values into empty placeholders so secrets aren't baked into a shared guide.

7  page The hands — guide-overlay.js

baymax-extension/public/guide-overlay.js

This is a classic content script (plain JS, no imports, wrapped in an IIFE) injected into every frame of the GCP console. It receives BAYMAX_GUIDE messages and does the physical work: find the element, draw the mascot, click/fill, and report back. Four subsystems: the resolver, the renderer, the watchers, and the recorder.

7.1  The message entry point

chrome.runtime.onMessage.addListener(function (msg, sender, sendResponse) {
  if (msg.type !== 'BAYMAX_GUIDE') return
  var result
  if (msg.action === 'highlight') result = highlight(intentFromMsg(msg), { title, message, stepAction, ... })
  else if (msg.action === 'click')  result = click(intentFromMsg(msg))
  else if (msg.action === 'fill')   result = fill(intentFromMsg(msg), msg.value)
  else if (msg.action === 'lost')   result = showLost({ title, message })
  // … clear / snapshot / record-start / record-stop …
  sendResponse(result)   // { ok:true } or { ok:false, error:'not-found' } → travels back to guide.js
})

intentFromMsg(msg) repacks the targeting fields (selector, extraSelector, role, name, text, href, avoid*, exactName, requireSelector, revealSelector, revealValue) into an intent object — the currency of the resolver.

7.2  The resilient resolver — the cleverest part

A single CSS selector breaks constantly on the GCP console (custom <mat-*> components, layout that changes when the instance list is non-empty, off-screen look-alikes). So instead of trusting one selector, the resolver scores every candidate element on the live page and picks the best visible one. Role + accessible-name beat brittle selectors.

Step 1 — gather candidates  (candidatePool)

  • Every element matching the step's selector (tagged fromSelector:true for a baseline boost).
  • Every element matching extraSelector (the self-heal channel — a live selector the backend picked).
  • Unless requireSelector is set: all interactive-ish elements on the page (a, button, input, mat-select, [role=…], etc.), so a moved element can still be found by name.

Step 2 — score each candidate  (scoreCandidate)

Signal Effect on score
Not visible -Infinity (disqualified)
Matched a selector +35
avoidText appears in the element -Infinity (drops "Enterprise Plus", doc/marketplace rows)
name exact match (exactName) +120, else disqualified
name exact / contains / in text +100 / +60 / +35 — no match at all → disqualified
text contains +25
role matches +20
href contains +25; avoidHref −100
In viewport +15
Is document.activeElement +30 (decisive for the focused search box)
Compact element (area < 90,000 px²) +5 new in doc
Long textContent penalty up to −12 (prefer the tight inner control, not the wrapping <div>)
The "name MUST match" rule. When a step names its target, a candidate that doesn't match the name scores -Infinity. This is why an un-rendered element makes the step return 'not-found' and retry instead of highlighting a random selector hit — pointing at the wrong thing is worse than waiting. resolveTarget only accepts a winner whose score clears ACCEPT_THRESHOLD (45); otherwise it returns null → {ok:false, error:'not-found'}.

new tryReveal(intent) — resurrect a transient panel

Some targets only exist while a transient panel is open — the "Cloud Run" search result lives in the search-suggestions dropdown, which closes the instant the user clicks "Show me"/"Do it for me" in the side panel (the page loses focus). A step can declare revealSelector, the control that summons the panel back: the overlay focuses/clicks it, refills it with revealValue if the console cleared it (via the native value setter + an input event so the framework notices), waits REVEAL_WAIT_MS (900ms), and re-resolves.

7.3  Rendering the highlight & mascot

All injected UI lives inside a Shadow DOM on one zero-size host element (ensureRoot), so the console's global CSS can't restyle the mascot and our styles can't leak into the page. On localhost the root is open (so tests can peek in); in production it's closed.

renderHighlight(el, reportKey, opts, intent) is the workhorse:

1
clearOverlay() — tear down any previous highlight and all its watchers.
2
Remember currentIntent / currentReportKey / currentOpts so the reposition loop can re-resolve later.
3
If the element isn't isWellInView (comfortably below the fixed top bar), scrollIntoView({block:'center'}).
4
buildMascot(opts) — the SVG Baymax + speech bubble (title/description) + "Step X of Y" board + cheer; and positionOverlay(el) — the pulsing outline box.
5
Attach scroll/resize repositioners + startReposition() (the rAF glue loop).
6
watchElement(el, reportKey) — report a user click. For inputs/fill steps also watchFill; for fill steps also watchFillFocus + watchFillDoc; for dropdowns watchOptionSelect.

The reportKey is intent.selector || intent.name — the exact string index.jsx compares against in onClicked/onFilled. That's the contract that ties "the user clicked this" back to "the current step is done".

The mascot positioning

positionMascot(el) stands Baymax to the element's right when there's room (his arm points left at it), flips him to the left otherwise — and when neither side fits (a full-width target like the top search bar) drops the whole column to rect.bottom + 16px, fully under the highlight, instead of clamping to the top of the viewport where the bubble used to cover the element. When the target scrolls out of view he fades out (baymax-offscreen) and waits with his element rather than chasing the user.

7.4  The self-healing reposition loop

startReposition() runs a requestAnimationFrame loop that keeps the outline glued to the target. It heals two failure modes seen on the create-instance form when a validation error appears:

  • The field moves (the error pushes it down): recompute its rect and reposition. Guarded by a cheap key (top,left,width,height) so it only restyles when the box actually changes — idle cost stays ~one rect read per frame.
  • The field is replaced (the framework re-renders the form, detaching the node): re-run resolveTarget(currentIntent) and reanchorHighlight onto the fresh node — an automatic "Show me" the user never has to press. Re-resolving is throttled (fast — 200ms — while the node is gone, otherwise every RERESOLVE_MS = 1200ms) so it never scans the DOM every frame.

7.5  Doing it for the user — click() and fill()

function click(intent) {
  var el = resolveTarget(intent)
  if (!el) return { ok: false, error: 'not-found' }
  renderHighlight(el, ...)
  setTimeout(function () {
    unwatchElement()          // stop watching FIRST, or we'd report our own click and advance twice
    clickTarget(el).click()   // mat-checkbox/radio: drill to the real inner input/label
    clearOverlay()
  }, 600)
  return { ok: true }
}

fill() is analogous: it focuses the element, sets .value via the native property setter (so React/Angular notice), then dispatches input + change events. It calls unwatchFill() first for the same reason — otherwise the dispatched event would also fire BAYMAX_GUIDE_FILLED and double-advance.

The Angular Material gotcha. A <mat-checkbox>/<mat-radio-button> host's own .click() does not toggle the control — only its inner native <input> (or <label>) does. clickTarget(el) drills down to that real toggle, while the highlight still frames the whole (bigger, visible) host.

7.6  The watchers — how the user's own actions complete a step

The whole point of "guide, don't take over" is that the user usually clicks themselves. Several watchers cover the ways they can act:

Watcher Catches Reports
watchElement A click on the highlighted element BAYMAX_GUIDE_CLICKED
watchFill Typing into the highlighted input (debounced 1.1s) BAYMAX_GUIDE_FILLED
watchOptionSelect Picking a mat-option in a CDK overlay appended to <body> (outside the control) BAYMAX_GUIDE_FILLED
watchFillFocus The user focusing a different real text field — re-anchors the highlight onto it —
watchFillDoc Typing anywhere on the page (the console search box swaps in a fresh input), debounced 1.1s BAYMAX_GUIDE_FILLED

watchFillFocus and watchFillDoc use e.composedPath()[0] so a field inside a web-component's shadow tree is seen as the real <input> (the bubbled event's target is otherwise retargeted to the shadow host, which has no .value). Both exist because the resolver has to pick a target before the user interacts, but the search box only reveals its real input once clicked.

7.7  Snapshot & recorder

collectSnapshot() returns a compact list of the page's visible interactive elements, each described the way the resolver reads them (role + accessible name + text + href) plus a live cssPath. Sending only elements that actually exist grounds any selector the self-heal LLM returns.

While recording, startRecording() attaches capture-phase click/input listeners. Each is fingerprintElement'd (the same signals the resolver reads back) and sent as BAYMAX_RECORD_ACTION. recordTarget redirects a bare <label> to the control it labels so the fingerprint has a stable role and name. This is the "write" side; the resolver is the "read" side of the exact same intent vocabulary.

8  End-to-end flow walkthroughs

Now the payoff — tracing a real command across all four files.

8.1  Opening a step (the happy path)

  1. data The step — index.jsx reads step = steps[safeStepIndex] (say step 6, "Name your instance", action:'fill').
  2. ui checkStep() — the effect asks getCurrentGcpUrl() (the pinned tab), confirms we're on engine=PostgreSQL (its urlPattern), then calls highlightStep(step, mascotExtras).
  3. bridge highlightStep() — spreads the step's fields into a {type:'BAYMAX_GUIDE', action:'highlight', …} message and sendGuideCommand broadcasts it to every frame of the tab.
  4. page The listener — guide-overlay.js receives it, intentFromMsg builds the intent, highlight() → resolveTarget() scores the page's inputs and picks the instance-ID field (name "Instance ID" wins).
  5. page renderHighlight() — scrolls it into view, draws the pulsing box + Baymax with the bubble "Name your instance" and "Step 6 of 10", and attaches watchFill. Returns {ok:true}.
  6. ↩ back through the chain — {ok:true} resolves sendGuideCommand → highlightStep → checkStep clears any status message. The user sees the highlight.

8.2  The user acts → the step advances (and is persisted)

  1. page User types "baymax-postgres" into the field. watchFill's debounce fires after 1.1s.
  2. page Report — send({type:'BAYMAX_GUIDE_FILLED', selector: reportKey, value}) → chrome.runtime.sendMessage.
  3. bridge Relay — the listener registered by onGuideStepEvent matches the type and calls onFilled(selector, value).
  4. ui Decide — onFilled checks selector === (step.selector || step.name); it matches, so autoAdvance() → goNext() → the departing step is PATCHed completed on the backend (markStepStatus) and setStepIndex(i+1).
  5. ↻ Loop — the step object changed, so the "on step change" effect re-runs, the arrival effect marks the new step in_progress, and step 7 opens exactly as in 8.1.

8.3  Auto-skip via URL (steps 1–2 disappearing)

  1. User is already on /sql/instances when the guide starts at step 1.
  2. ui checkStep() calls getCurrentGcpUrl(); stepCompletedByUrl(step1, url) is true and we're atFrontier() (and Back wasn't just pressed) → autoAdvance().
  3. Step 2 re-runs the same check, also passes → auto-advances again. The search lead-in silently evaporates and the user lands on step 3.

8.4  Wrong page → "Take me back"

  1. On step 5 ("Choose PostgreSQL", urlPattern:'/sql/choose-instance') the user clicks MySQL and lands on a MySQL form.
  2. bridge onGcpUrlChanged fires (it's the pinned tab) with the new URL.
  3. ui stepCompletedByUrl is false (MySQL form ≠ engine=PostgreSQL) and isOnStepPage is false → setOffTrack(true), setStatusMessage(OFF_TRACK_MESSAGE), showLostMascot().
  4. page showLost() draws Baymax at the edge with a "← Take me back" button (top frame only).
  5. User clicks it → BAYMAX_GUIDE_GO_BACK → onGoBack → handleTakeMeBack → goToStepPage(step): chrome.tabs.goBack, wait 500ms, verify the landed URL — hard-navigate to step.url if still wrong — then re-highlight after 1.5s.

8.5  "Do it for me"

  1. ui handleDoItForMe → runStepAction(step).
  2. bridge runStepAction sends {action: step.action==='fill' ? 'fill' : 'click', …, value}.
  3. page click()/fill() resolves + highlights, un-watches (so it doesn't report its own synthetic action), then programmatically clicks/fills.
  4. ui Because the overlay stayed silent, index.jsx advances itself: submit steps call verifySubmit(); everything else setTimeout(…, 800) — which fires only if stepIndexRef still equals the index the button was pressed on (a navigating click may have advanced the guide already).

8.6  The highlight healing itself (no round-trip)

This one lives entirely inside guide-overlay.js. On the create form, entering a duplicate instance ID makes Angular re-render the field. The old node the outline was glued to is detached. The rAF startReposition loop notices !el.isConnected, re-runs resolveTarget(currentIntent), finds the fresh field, and reanchorHighlights onto it — outline, mascot, and watchers all follow, with no message to the panel and no user action.

8.7  Recording a guide

  1. bridge startRecording() → resetGuidedTab() (adopt the tab the user is on now) → {action:'record-start'}.
  2. page attaches capture-phase click/input listeners. Each user action → fingerprintElement → BAYMAX_RECORD_ACTION.
  3. bridge onRecordedAction(cb) streams each to the UI, which builds a draft (collapsing click-then-type into one fill step, dropping exact repeats).
  4. On save, recordedActionToStep converts each fingerprint into a step (values → placeholders), and applyGeneric/volatileTokensFromUrl optionally strip instance-specific ids so it replays anywhere. The result is a guide object shaped exactly like the bundled guides — which index.jsx then drives identically.

9  Design patterns worth internalising

Pattern Where Why it exists
Intent over selectors resolver in overlay GCP's DOM is a moving target; role + accessible name survive redesigns that break CSS selectors.
Scoring, not matching scoreCandidate Multiple elements can plausibly match; scoring + a threshold picks the best visible one and rejects look-alikes.
The frontier rule maxReachedRef Stops URL-based auto-skip from cascading the user forward when they deliberately press Back.
One progress source new markStepStatus The backend step status is the only store; a second (localStorage) source made fresh runs inherit abandoned progress.
Pinned tab identity new guidedTabId The guide follows one tab by id, not whichever GCP tab has focus — no hijacked highlights or phantom off-track.
Local steps authoritative new load effect The backend's step copy is lossy (drops resolver fields); it may resume a run but never replace live steps.
Report key = selector‖name overlay ↔ index.jsx A single agreed string lets "the user clicked X" map cleanly to "step X is done", even for generalised steps.
Un-watch before acting click/fill Prevents a synthetic action from also firing the user-action event and double-advancing.
Navigation = proof awaitNavigation A click on a submit button isn't success; only landing on the next page is.
Shadow DOM isolation ensureRoot The console can't restyle Baymax and Baymax can't leak styles into the console.
Broadcast to all frames sendGuideCommand The real target often lives in a same-origin iframe, not frame 0.
Graceful degradation everywhere Every path fails to a readable status message, never a crash — the guide is a helper, not a blocker.
The whole system in one loop:
index.jsx picks a step (from a bundled, recorded, official, or AI guide) → guide.js messages it to the pinned tab → guide-overlay.js resolves + highlights it and watches the user → the user acts → guide-overlay.js reports it back → guide.js relays the event → index.jsx advances stepIndex and persists the status to the backend → the loop repeats until the last step calls finish().
